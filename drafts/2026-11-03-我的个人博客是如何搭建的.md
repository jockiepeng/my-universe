# 我的个人博客是如何搭建的

现在看到的「jockie 的小宇宙」，是我用 VS Code、Codex CLI 和 Superpowers 逐步搭起来的个人博客。

**整个搭建过程，我没有自己写一行代码，完全通过自然语言与 AI 交流。** 从页面设计、代码编写，到功能扩展、问题排查和部署配置，都交给 AI 完成。我负责决定想做什么、查看实际效果，再把不符合预期的地方反馈给它。

比如“把文章分成技术和生活两大类”“手机上按钮太挤了，调整一下”“增加一个可以保存进度的 2048 游戏”，这些都是我给 AI 的需求。代码由 AI 编写，启动服务和运行检查的命令，也可以让它在授权范围内执行。

前面那篇《AI探索：先搭工具箱，再让 AI 帮我做一个博客》，记录了最初如何准备工具、跑通开发和部署。这一篇想接着聊聊：现在的博客用了哪些技术，已经有哪些功能，以及 AI 在搭建过程中具体做了什么。

这一篇介绍整体结构、功能和协作方式，也会简单解释小游戏的规则与渲染、AI 调试的过程。更深入的代码细节，后面可以分别展开。

## 从一个可以持续写作的地方开始

我希望有一个自己的地方，用来整理技术实践、记录生活，也放一些值得留下来的图片。

对这个博客来说，最基本的要求是写文章方便、阅读舒服、后续能持续修改。除此之外，我也想让它有一点自己的样子：有不同的背景，有进入网站时的小动画，还可以放几个小游戏。

这些需求逐步形成了现在的结构：以文章为中心，把分类、搜索、评论和阅读量补齐，再增加一些个人化的体验。

技术上，博客采用 Astro 生成静态页面，通过 GitHub Pages 托管。文章用 Markdown 管理，我不需要为网站单独维护一台持续运行的服务器。

## VS Code、Codex CLI 和 Superpowers 分别做什么

这三个工具经常一起出现，但各自负责的事情不同。

**VS Code 是查看和管理项目的工作台。** 我可以在里面打开目录、阅读文章和代码、查看修改记录，也可以使用终端启动项目。早期的工具探索还用过 VS Code Remote SSH，连接云服务器上的开发环境；当前这套博客也可以直接在本地开发。

**Codex CLI 是参与开发的 AI 编程工具。** 它在终端里工作，可以在授权范围内读取项目文件、修改代码、运行命令和检查结果。比如我提出“首页加一个分类筛选”，它需要先看现有文章如何分类、页面怎么组织，再修改相关文件，而不是只给我一段需要自己拼进去的代码。

**Superpowers 是帮助 AI 按步骤工作的技能和工作流集合。** 我说的“Super Skill”，这里具体指的就是 Superpowers。它不是另一种编程语言，也不是网站运行时需要加载的插件；它主要影响 AI 如何理解需求、制定计划、编写代码和排查问题。

在这个项目里，可以这样理解它们的配合：我提出需求，在 VS Code 中查看项目和预览效果；Codex 执行具体开发任务，Superpowers 为需求梳理、实现和验证提供流程约束。

网站发布之后，读者访问博客并不需要安装这些开发工具。

## 博客用到了哪些技术

如果只看 HTML、JS、TS 这些名字，容易觉得它们都在“写网页”。放进具体项目里，它们的分工就清楚一些了。

| 技术或工具 | 在博客中的作用 |
| --- | --- |
| Astro | 组织页面、布局和组件，把文章与模板构建成静态网站 |
| HTML | 承载标题、正文、导航、按钮等页面结构 |
| CSS | 控制排版、颜色、深浅色主题、手机布局和部分动画 |
| JavaScript | 实现筛选、日期计算、游戏规则等逻辑 |
| TypeScript | 编写页面交互，并通过类型检查提前发现一部分错误 |
| Markdown | 编写和保存文章正文 |
| WebGL、Canvas 2D | 绘制首页动态背景和部分入场效果 |
| Pagefind | 生成静态搜索索引，提供中文全文搜索 |
| giscus、不蒜子 | 分别接入评论和文章阅读量 |
| Node.js、npm | 在开发和构建时运行工具、管理依赖 |
| Git、GitHub、GitHub Actions、GitHub Pages | 管理版本、保存代码、自动检查并部署网站 |

其中，TypeScript 可以理解为增加了类型约束的 JavaScript。它帮助开发时检查数据和接口是否用对，最终交给浏览器执行的仍然是 JavaScript。

Astro 则把这些部分组织起来。比如文章页可以共用一套布局，导航和评论区可以拆成组件，文章内容从 Markdown 中读取。这样增加文章时，不需要重新写一整个网页。

这里的“静态网站”，是指主要页面在构建时就已经生成，并不意味着页面只能展示固定内容。主题切换、搜索和小游戏仍可以在浏览器里运行；评论和阅读量则通过外部服务获取数据。

## 文章是什么格式，又存在哪里

博客文章使用 **Markdown 格式**，每篇文章都是一个 `.md` 纯文本文件。标题、段落、列表、链接和代码块都可以用简单标记表达，便于在 VS Code 中查看，也方便交给 AI 整理。

内容分成两个位置存放：

- `drafts/` 是文稿箱，存放想法和初稿，只写正文即可，不参与博客构建。
- `src/content/posts/` 是文章目录，存放准备交给博客系统处理的内容，每篇文章包含顶部配置和下面的正文。

顶部配置叫 frontmatter，使用 YAML 格式，记录标题、固定链接、日期、分类、标签和草稿状态。下面是一篇文章的结构示例，这些配置也可以由 AI 根据我的要求填写：

```markdown
---
title: 我的个人博客是如何搭建的
slug: how-i-built-my-blog
date: 2026-11-03T20:00:00+08:00
category: 技术/AI
tags: [个人博客, Codex, Superpowers]
kind: post
draft: true
---

这里开始写文章正文。

## 一个小标题

这里是这一节的内容。
```

其中 `slug` 决定文章的固定地址；`draft: true` 表示草稿，只在本地开发模式展示，正式构建会排除。日期字段用于展示和排序，不代表到时间就会自动发布。

配图可以放在文章旁的文件夹中，通过相对路径引用；贴图类型则把图片列表放进顶部配置，正文保留为纯文字。文章和图片先保存在本地项目目录，提交、推送后随代码一起保存在 GitHub 仓库里，由 Git 记录修改历史，不需要额外的文章数据库。

发布时，Astro 读取这些文件，把 Markdown 转成 HTML，并套用统一的文章布局，生成到 `dist/`。GitHub Pages 托管的是生成后的静态文件。平时写作只需要维护原始文章，页面排版、目录和相关索引由构建流程处理。

这里也有一个需要分清的地方：文章和配图在仓库里，评论在 GitHub Discussions 中，阅读量在不蒜子服务中，它们并不是同一份存储。

## 现在的博客有哪些功能

### 文章、贴图和内容整理

博客支持普通文章和贴图两种内容形式。普通文章适合技术记录和长文，支持目录、代码高亮、图片和表格；贴图则在详情顶部展示可横向切换的图片，下方放文字，适合保存一些图文记录。

内容可以按照主题和标签查找。目前分类支持父子层级，例如“技术 / AI”和“生活 / 人际关系”。首页可以先选择一级分类，再选择子分类，也可以叠加“文章 / 贴图”筛选。

另外还有日期归档和分页，文章多起来之后，也能沿着不同入口找到以前写过的内容。

### 中文全文搜索和阅读辅助

搜索使用 Pagefind，在构建网站时生成索引，读者可以直接搜索文章正文，不需要再搭一个搜索服务器。完整搜索体验需要在构建后预览，单纯启动开发服务与正式站点会有区别。

阅读方面，博客提供长文目录、预计阅读时间、返回顶部，以及适配手机的排版。代码块和宽表格可以横向滚动，避免把整篇文章撑出屏幕。

此外还生成 RSS 和站点地图，方便订阅与内容发现。

### 文章阅读量

文章详情页的阅读量接入了不蒜子。读者打开正式文章后，浏览器从统计服务获取该页面的累计访问次数，再把数字显示出来。

这里统计的是页面浏览次数，也就是 PV。刷新或重复打开可能继续增加，所以“阅读 100 次”不能直接理解为“有 100 个不同的人读完了文章”。

本地开发和本地预览不会请求真实计数。服务暂时不可用时，页面保留占位提示，正文仍然可以正常阅读。

阅读量数据保存在第三方服务中。只要正式文章地址保持不变，重新构建和部署本身不会清零计数；更换域名或文章路径，则可能影响原有统计的关联。

### 评论

评论采用 giscus，背后的数据保存在 GitHub Discussions。这样就不需要自己开发一套评论后端和数据库。

完成仓库授权和配置后，读者可以查看讨论，使用 GitHub 账号发表评论、回复或添加表情。管理者也可以直接在 GitHub Discussions 中管理这些内容。

评论区域接近屏幕时才加载，并跟随网站的深浅色主题切换。配置尚未完成时，页面会提示“评论暂未开放”；加载失败时，也保留前往 GitHub 讨论区的入口。

### 动态背景和入场动画

首页有三种背景：星系漫游、极光之境和日落海面；入场则有粒子汇聚和星门开启两种效果。

这些效果由原生 WebGL、Canvas 2D 和 CSS 实现。默认组合按照北京时间当天日期的尾号分配，同一天保持一致，也可以手动切换或重播。

为了照顾阅读体验，明显的动态效果集中在首页，文章阅读背景保持静态。读者可以关闭动态，网站也会尊重系统的“减少动态效果”设置；不支持 WebGL 时，则保留静态背景。

对我来说，动画主要是给网站增加一点个人特色，正文是否清楚、操作是否顺手，仍然要优先考虑。

### 时间、日历和随想

导航里的时间入口可以展开查看北京时间、月历和节日倒计时，日历支持翻月、跳转指定年月和回到本月。

首页的“随想”按北京时间日期从文案库中选择句子，同一天刷新或换浏览器，显示的内容保持一致，跨日后重新选择，也可能连续选到同一句。

这些功能不需要额外后台，日期计算和展示主要在浏览器里完成。

### 小游戏

博客还增加了一个游戏大厅，目前有三骰猜大小、2048 星球合成、星际贪吃蛇、星域扫雷、星际打砖块和星图连连看。

这些游戏用的是浏览器原生技术。HTML 提供棋盘、按钮、分数栏和 `<canvas>` 画布，CSS 负责布局、颜色和动效，JavaScript / TypeScript 负责处理输入、计算规则和更新画面，没有额外引入大型游戏引擎。

游戏根据玩法支持键盘、鼠标或手机触屏操作，部分还提供难度选择、暂停、最高分和进度保存。记录通过 `localStorage` 保存在当前浏览器中，不会跨设备同步。三骰猜大小使用虚拟金币。

小游戏让网站多了一点可以停留和探索的空间，也给 AI 编程提供了很直接的检验方式：规则是否正确，操作是否流畅，手机上是否真的能玩，都要实际运行才能知道。

## 小游戏怎样计算规则和渲染画面

它们共用一个基本思路：**先用数据记录游戏状态，接收操作后计算新状态，再把状态绘制到页面上。** 比如蛇身是一组坐标，2048 棋盘是一组数字，小球则有位置和速度。画面跟着这些数据变化。

渲染主要有两种方式。贪吃蛇和打砖块使用 HTML 的 Canvas 2D 画布，通过绘图接口画出蛇、食物、小球、挡板和砖块；扫雷、连连看、2048 和骰子主要使用 DOM，也就是页面里的格子、按钮等 HTML 元素，通过 CSS Grid 排列，再更新文字、样式或位置。连连看的连接线另外使用 SVG 折线展示。

### 贪吃蛇

蛇身在程序中是一串从头到尾排列的格子坐标。每隔一段时间，程序根据方向计算新蛇头：向右就是横坐标加一，向上就是纵坐标减一。

普通移动时，把新头放进数组，再删除旧尾，长度保持不变；吃到食物时保留旧尾，于是蛇身增加一格，同时加 10 分。下一颗食物从没有被蛇占用的空格中随机选择。

新头越过棋盘边界或撞上身体，就判定失败；不允许直接向当前方向的反方向掉头。每次更新后重画 Canvas，连续看起来就是蛇在移动。速度档位控制的是两次移动之间的时间间隔。

### 2048 星球合成

棋盘是一个 4×4 的数字数组。玩家滑动或按方向键后，程序按移动方向逐行或逐列处理：先挤掉空位，再将相邻且相等的数字两两合并，最后补齐空格。

例如一行 `2、2、2、2` 向左移动，会变成 `4、4、空、空`，同一步刚合成的数字不会再次合并成 8。分数增加量是本步合成数字的总和。

只有棋盘实际变化时，才会在一个随机空格中生成新数字，90% 的概率是 2，10% 是 4。没有空格且相邻格也无法合并时结束；合成 2048 后可以选择继续。

界面把不同数字对应成不同星体，用 HTML 元素展示棋盘，通过 Web Animations API 播放位移动画，再更新合并结果。星球外观是数字状态的视觉表达，不涉及真实天体物理模拟。

### 扫雷

每个格子记录是否有雷、周围雷数、是否翻开和是否插旗。地雷在第一次有效翻格时才生成，而且会避开点击格及其周围八格，保证首击及周边安全。

程序打乱其余候选位置，选出规定数量的格子放雷，再计算每个格子周围八格的地雷数。点击数字为 0 的格子时，会继续检查相邻格，向外展开连通的空白区域，直到显示出周围的数字边界。

踩雷则失败，翻开所有非雷格则获胜，不要求每颗雷都插旗。棋盘由 HTML 格子按钮组成，程序根据状态切换数字、旗帜和地雷的显示。

### 打砖块

小球记录位置与速度，每次更新按照“位移 = 速度 × 经过时间”计算新位置。浏览器通过 `requestAnimationFrame` 安排下一帧，程序更新状态后重画 Canvas。

碰到左右墙时改变水平速度方向，碰到顶部时改变竖直方向。落到挡板上时，根据落点偏离挡板中心的程度调整反弹角度，因此玩家可以通过接球位置控制球的方向。

碰到砖块时，程序判断球与矩形是否接触，再根据接触方向反弹、移除砖块并加分。为减少高速穿过砖块的问题，一帧的移动会拆成多个小步检查碰撞。

球掉出底部扣一条生命，三条生命耗尽则结束；清空砖块可以进入下一关，球速和挡板宽度随关卡调整。

### 连连看

棋盘先生成成对的图案，再打乱位置。选择两个相同图案后，程序搜索一条连接路径：可以经过空格和棋盘外围，但不能穿过其他图案，最多只能转弯两次。

搜索时同时记录位置、前进方向和已转弯次数，超出两次转弯就放弃该路线。找到合法路径后，短暂画出 SVG 连接线，消除这一对并加分；限时内消完则获胜。

提示功能会用同一套规则寻找可消的一对。洗牌只打乱剩余图案，保留已经消除的空位，并检查至少有一对可以连接；消除后出现死局，也会自动洗牌。

### 三骰猜大小

开骰时使用浏览器的随机数接口生成三个 1～6 的点数，再计算总和。4～10 为小，11～17 为大，但三个点数完全相同的“豹子”会让大小下注都输；押具体总点数则按总和单独结算。

结算时先扣除本局全部下注，再按中奖位置的赔率计算返还，中奖会退回对应本金。程序记录每轮骰子、下注、盈亏和余额，再由历史记录汇总统计。

骰子的点数由 HTML 元素和 CSS 展示，摇动只是反馈动画，最终输赢由生成的点数和结算规则决定。

## 博客是怎样一步步搭起来的

整体过程可以概括为：需求描述、原型确认、分步实现、本地验证，再提交部署。

最初需要说清楚的，是自己想要一个怎样的博客：写什么内容，喜欢什么布局，是否需要评论和搜索，希望部署在哪里。像“做得好看一点”这样的要求太宽泛，补充参考页面、截图或具体反馈后，AI 才更容易理解。

项目里保留了前期原型，以及设计文档和实施计划。确定方向后，再把页面结构、文章管理、搜索、评论和阅读量拆开完成。后来的动态场景、贴图、游戏和分层分类，也是在原有基础上逐步增加的。

每次调整后，我会让 AI 启动本地开发服务，再用浏览器查看效果。对应的命令是下面这些；它们也由 AI 执行，不需要我自己编写脚本：

```sh
npm run dev
```

需要检查正式构建效果，尤其是搜索时，再运行：

```sh
npm run build
npm run preview
```

本地看起来正常之后，还要运行项目检查。代码推送到发布分支 `main` 后，配置好的 GitHub Actions 会安装依赖、执行验证、构建网站，再发布到 GitHub Pages。

这里也要区分开发环境和网站托管：早期尝试过的云服务器可以用来运行开发工具，但当前博客的公开页面由 GitHub Pages 托管，访客不依赖我的开发电脑在线。

## 我怎样使用 Superpowers

**完成安装、让 Codex 能识别这些技能后，平时只需要用自然语言描述需求，AI 会根据任务自动选择和使用适用的技能。** 不需要记住每个技能名称，也不需要每次手动调用。安装方式可以参考 [Superpowers 项目说明](https://github.com/obra/superpowers)。

技能通常通过 `SKILL.md` 描述适用场景和工作步骤。AI 识别到任务属于功能设计、问题排查或完成验证时，就读取相应说明，再按照里面的流程工作。

Superpowers 的功能点主要包括：

| 功能点 | 帮助 AI 做什么 |
| --- | --- |
| 需求梳理与方案讨论 | 阅读现有项目，澄清目标、约束和预期效果，比较可行方案 |
| 实施计划与执行 | 把需求拆成具体任务，明确修改范围，按步骤实现 |
| 测试驱动开发 | 对适用的功能先用测试描述预期行为，再编写实现 |
| 系统化调试 | 先收集证据、复现和定位原因，再针对原因修复 |
| 代码审查 | 检查修改是否符合需求，是否引入遗漏或其他问题 |
| 完成前验证 | 运行相关检查，确认结果后再报告完成 |
| Git 工作区与分支管理 | 在需要时隔离开发改动，帮助整理完成后的代码 |

比如我只需要说：

> 给博客增加父子分类，首页可以按分类筛选，手机也要方便使用。

AI 就可以根据任务先梳理需求，再制定计划、修改代码和验证效果。项目中的 `docs/superpowers/specs/` 和 `docs/superpowers/plans/` 就保存了这类设计文档和实施计划，方便后续继续修改。

遇到问题时，也可以直接说：

> 阅读量在网络慢的时候会显示异常，帮我查一下原因并修好。

这类任务适用系统化调试流程，正常使用时不用再额外输入技能名。如果想强调某个步骤，也可以主动要求“先复现再修改”或“完成后检查手机上的效果”。

不同任务会采用不同的技能组合，修改一句文案与增加一个游戏模块，不需要走完全相同的流程。Superpowers 提供的是工作方法；浏览器操作、命令执行等能力，仍需要 Codex 环境中相应的工具支持。自动选择技能也不等于结果一定正确，最后仍要检查需求和实际效果。

## AI 是怎样调试问题的

在这个项目里，AI 调试会结合代码、报错和实际运行结果。逻辑问题可以用测试检查，页面问题则需要打开浏览器，观察界面、模拟操作，有时还要检查网络请求或对照截图。

### 从问题描述到修复验证

调试通常沿着这样的顺序进行：

1. **明确现象和预期。** 哪个页面、什么操作、在什么条件下出了问题，正常应该是什么样。
2. **收集证据。** 阅读相关代码，检查终端报错、浏览器脚本异常、页面状态和网络请求。
3. **建立假设并复现。** 怀疑是加载顺序、超时、存储还是布局问题，就控制相关条件，验证能否稳定触发。
4. **针对原因修改。** 根据证据修正相关逻辑，再用相同条件检查原问题。
5. **检查相关功能。** 确认修复没有破坏其他页面、手机操作或已有行为。

这里的关键是让假设接受实际运行结果的检验。例如怀疑问题来自慢请求，就延迟响应观察状态变化；怀疑是手机宽度导致按钮被遮挡，就切换视口并检查元素位置。每一步都在缩小原因范围。

### AI 怎样驱动真实浏览器

这个项目安装了 `playwright-core`，浏览器检查脚本由 AI 编写，再通过终端工具运行。脚本启动一个本地 HTTP 服务，把构建后的页面提供出来，然后调用 Playwright 启动机器上已安装的 Chrome 或 Chromium，访问对应地址。

Playwright 是浏览器自动化工具。它通过浏览器的控制接口发送操作指令，让浏览器完成打开页面、点击按钮、输入搜索词、按方向键、滚动和刷新；同时可以读取 DOM 元素的文字、属性、位置及可见状态，监听脚本异常、检查网络请求并保存截图。

例如检查 2048 时，脚本可以打开游戏页、发送向左按键，再读取棋盘数字、分数和步数，判断合并是否正确。检查手机交互时，会设置较窄的视口和触屏环境；项目中的部分滑动测试还通过 Chrome DevTools Protocol，也就是 Chrome 的调试协议，发送触摸开始、移动和结束事件，让浏览器处理完整手势。

这里运行的是完整的浏览器引擎，会实际加载 HTML、执行 JavaScript、应用 CSS 和渲染 Canvas。检查脚本默认使用无头模式，也就是不弹出可见窗口，但页面仍会真实渲染，并不是只对着源代码推测效果。

可以把过程理解为：我描述问题，AI 编写或调整检查脚本，通过终端执行，Playwright 控制浏览器，脚本输出检查结果和截图，AI 再据此分析和修改。截图用于检查视觉效果，页面数据和断言用于确认行为，二者配合使用。

### 阅读量迟到响应的实际案例

一个具体例子是文章阅读量的迟到响应。

统计还没返回时，页面先显示“阅读 — 次”。开发过程中曾出现过这样的问题：请求超时后，数字又迟了一会儿返回，最终占位符和数字同时显示，变成“阅读 —42 次”。

这类问题在网络顺畅时很难碰到，所以需要主动制造相同条件。

当时的处理过程是：

1. 在浏览器自动化检查中拦截计数请求，延迟返回结果，稳定复现异常。
2. 检查超时处理和数字更新逻辑，定位迟到结果没有正确清除占位状态的问题。
3. 调整逻辑，让超时后返回的有效数字仍能正常展示，同时隐藏占位并恢复提示。
4. 再运行同一场景，检查数字、占位和状态提示是否都符合预期。

测试中的 `42` 是模拟响应，用来验证页面显示，不是真实阅读量。计数接口响应被拦截，也避免了测试反复访问造成真实统计增长。

这个例子让我更容易理解 AI 编程里的“验证”：生成一段看起来合理的代码，只完成了其中一部分。还需要重现原来的问题，检查修改后是否恢复正常，并确认相关功能没有被影响。

除了这个案例，浏览器脚本还检查手机布局、主题切换、搜索、滚动和游戏操作，也覆盖了关闭 JavaScript、减少动态效果、浏览器存储不可用等情况。

项目把常规验证整理成了一个命令：

```sh
npm run verify
```

它会执行单元测试、Astro 模板与类型检查、静态构建和产物检查，包括检查链接，以及草稿是否意外进入正式网站、搜索、RSS 或站点地图。浏览器交互检查则有单独的脚本。

构建检查可以发现一部分问题，浏览器检查可以发现另一部分；涉及第三方评论、计数和正式部署地址的地方，还需要结合实际环境确认。

## 后面怎样继续维护

现在写新内容，可以先放进文稿箱，再让 AI 整理正文、补齐文章配置，放到文章目录中保留为草稿。确认发布时，再让它调整状态并执行后续流程。

后续增加功能，也可以继续沿用这套方式：先说明想解决什么问题，让 AI 阅读现有实现，再给出方案、完成修改和验证。

接下来我想分别记录阅读量、giscus 评论、动态背景和小游戏的具体实现，也把遇到的调试问题保留下来。这样博客既是写作的地方，也能成为这次 AI 编程实践持续更新的记录。

对我而言，这次搭建最大的变化，是把原来停留在想法里的需求，一点点变成了可以打开、可以使用、也可以继续修改的网站。全程没有自己写一行代码，需求、调整意见和问题反馈都通过自然语言表达。我需要做的，是把需求说清楚、认真看结果，并在出现问题时继续追问和验证。
